IRIS Calibration Simulation Plots

Load one or more outputs/csv/*_body*.csv files (per-body logs) to compare Leapfrog-vs-IAS15 calibration runs. Each log only contains one row per correction event that THIS BODY actually triggered -- i.e. this body's own error, not just the system-wide RMS error, crossed the correction threshold -- see calibration/logger.py.

Scroll to zoom a chart, drag to pan, double-click to reset.
Per-correction-event metrics (per loaded body log)

Position Error vs Time

RMS position error between Leapfrog and IAS15 for this body, at each correction event (log scale). Only correction timestamps are logged now, so each marker is one correction -- the dashed line between markers is just a visual guide, not a continuous trace.

Velocity Error vs Time

RMS velocity error between Leapfrog and IAS15 for this body, at each correction event (log scale). Same caveat as Position Error vs Time: markers are real samples, the connecting line is not.

Energy Drift vs Time

Relative drift of total system energy from its initial value, sampled at each correction event.

Angular Momentum Drift vs Time

Relative drift of total system angular momentum magnitude, sampled at each correction event.

Min Pairwise Distance vs Time

Closest approach between any two bodies in the system, sampled at each correction event.

Total Energy vs Time

Kinetic + potential energy of the Leapfrog trajectory, sampled at each correction event.

Max Acceleration vs Time

This body's gravitational acceleration magnitude, sampled at each correction event.

Jerk vs Time

Finite-difference estimate of da/dt for this body, sampled at each correction event.

Correction Events vs Time

Each point is a moment a correction fired AND this body's own error was one of the ones that crossed the threshold (calibration/logger.py only logs a correction to bodies that actually triggered it, not every body of the system); y = THIS body's own position error at that instant (the pre-correction Leapfrog state vs. the IAS15 state it was snapped to). Hover a point to also see the system-wide RMS error that actually triggered the correction. Only rendered for CSVs produced with the online correction mechanism (core.leapfrog.run_leapfrog_with_correction).

Situation Timeline (same time axis as above)

One row per situation type; a marker means that situation was active for that body at one of ITS OWN correction events (only rows where this body's own error crossed the threshold are logged at all -- see calibration/logger.py). Shares the exact time domain with the "Correction Events vs Time" chart above (and stays synced when you pan/zoom either one); each marker corresponds directly to a row in that scatter plot -- look straight up from a point there to see which situations coincided with it. "stable" is intentionally left out (it's the default, non-event state); "quiescent_regime" is kept since it only marks a genuinely sustained calm stretch.

Correction Interval vs Time

At each correction event, the elapsed simulated time since the PREVIOUS correction: a rising trend means corrections are getting rarer (the run is stabilizing); a falling trend means they're getting more frequent (destabilizing). This replaces the old "time since last correction" sawtooth view, which needed dense per-timestep samples that are no longer logged (every logged row is now itself a correction, so that value was always 0). correction_id/correction_interval are SYSTEM-wide (identical wherever a correction appears at all), but each body's file now only contains the corrections IT OWNED (its own error crossed the threshold, not just the system-wide RMS -- see calibration/logger.py), so no single loaded file is guaranteed to hold the full timeline any more. One line is drawn per loaded simulation, reconstructed from the union of every loaded body's own correction_id rows for that simulation (every correction is guaranteed to be owned by at least one body, so nothing is lost).
Correction diagnostics

Situations Distribution (Pie Chart)

Share of total situational-event activations by type, summed across every correction-event row of every visible file (each row is a correction that body itself triggered, not merely one that occurred somewhere in the system -- see calibration/logger.py -- so this reflects what tends to be happening at a body's OWN corrections, not over the whole run). Situations are not mutually exclusive (several can be true on the same row), so slices reflect relative frequency of each situation type, not a partition of time.

Number of Corrections vs Situation (Histogram)

Counts how many of THIS BODY'S OWN corrections coincided with each detected situation (calibration/events.py flags) -- since calibration/logger.py only logs a correction to bodies whose own error crossed the threshold, this is no longer every correction in the system, just the ones this body was responsible for. Bars are stacked per loaded file. A situation with a tall bar is one that tends to force this body specifically into triggering a correction. (Every logged row is now a correction event, so this covers the whole file.)

Correction Interval Distribution (Histogram)

Distribution of elapsed simulated time between consecutive corrections (correction_interval), reconstructed per simulation from the union of every loaded body's own corrections and deduped by correction_id, so an event logged by more than one body (multiple bodies can cross the threshold at once) is only counted once. Bars are stacked per simulation.

Minimum Pairwise Distance with Correction Events Overlay

system_min_distance at each of THIS BODY'S OWN correction events (dashed line, for trend), with a triangle marker on every point for emphasis. Since only this body's own corrections are logged (see calibration/logger.py), the line and the overlay are the same points by construction, and different bodies of the same run will show different subsets of triangles -- kept as two layers mainly so individual correction events stand out clearly against the trend line.

Error Growth Between Corrections (Normalized)

error_at_trigger / correction_interval at each correction event: how fast error accumulated per unit simulated time before the correction fired.

Energy Drift vs Number of Corrections

One point per loaded BODY: mean energy_drift across this body's own correction events vs. the number of corrections this body itself triggered (calibration/logger.py only logs a correction to bodies whose own error crossed the threshold -- see comparer.py's body_triggered_correction -- so both the sample count and the x-value now genuinely differ from body to body, even within the same run).

Angular Momentum Drift vs Number of Corrections

One point per loaded BODY (same reasoning as the Energy Drift chart above): mean angular_momentum_drift across this body's own correction events vs. the number of corrections this body itself triggered.
Encounter & accuracy relationships (at correction events)

Position Error vs Minimum Pairwise Distance

At each correction event: does Leapfrog accuracy degrade as bodies get closer together? Both axes log scale.

Velocity Error vs Minimum Pairwise Distance

Same question for velocity error, at each correction event. Both axes log scale.

Relative Velocity vs Minimum Pairwise Distance

At each correction event: this body's relative velocity to its nearest neighbor vs. the system's minimum pairwise distance -- separates "slow" from "fast" close encounters.

Jerk vs Position Error

At each correction event: tests whether jerk is a good predictor of Leapfrog error. Both axes log scale.

Maximum Acceleration vs Position Error

At each correction event: tests whether acceleration magnitude alone predicts Leapfrog error. Both axes log scale.
Integrator trade-off

Accuracy vs Computational Cost (Pareto Curve)

"Hybrid Scheduler" points are real, one per loaded body: x = number of corrections THIS BODY itself triggered (calibration/logger.py only logs a correction to bodies whose own error crossed the threshold, so this is this body's own count, not the run's total -- still a reasonable per-body cost proxy, since every correction it owns means an extra IAS15 re-sync it needed), y = mean of body_position_error_at_trigger (this body's own pre-correction error at each of its own correction events -- the log no longer contains post-correction/ steady-state samples to average instead). "Leapfrog" approximates the uncorrected integrator using body_position_error_at_trigger from just this body's FIRST own correction -- the error that accumulated before this body needed correcting for the first time, which is the only uncorrected-Leapfrog signal still present now that only (owned) correction timestamps are logged. "IAS15" is plotted as a single high-cost, near-zero-error reference anchor, since IAS15 is the ground-truth trajectory itself. NOTE: the per-body CSV schema does not log wall-clock integration time, so the x-axis here is a cost proxy, not measured seconds -- treat this chart as illustrative of the accuracy/cost trend, not an absolute benchmark.
